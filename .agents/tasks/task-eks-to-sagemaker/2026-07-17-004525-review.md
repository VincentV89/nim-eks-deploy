# EKS-to-SageMaker migration for NVIDIA NIM inference

The entire deployment stack for Llama 3.1 8B Instruct has been replaced: VPC + EKS + Kubernetes manifests + Helm charts are gone, replaced by a Terraform-managed SageMaker real-time endpoint with Application Auto Scaling. The deploy script becomes a thin terraform-apply wrapper, and the load test switches from async HTTP (aiohttp) to synchronous boto3 `invoke_endpoint` calls in a thread pool. The migration is structurally sound — the SageMaker resources chain correctly and autoscaling targets the right metric.

**Watch for:** NGC API key stored in plaintext in the SageMaker model environment (confirmed), IAM role uses `AmazonSageMakerFullAccess` managed policy instead of least-privilege (confirmed), load test has race conditions on shared mutable `stats` dict from multiple threads (confirmed), and deploy script's region extraction is fragile (confirmed).

## High-level view

The Terraform layer replaces ~100 lines of VPC/EKS module declarations with a linear chain of SageMaker resources: IAM role, model definition, endpoint configuration, endpoint, and autoscaling policy. The autoscaling configuration targets `SageMakerVariantInvocationsPerInstance` at 100 invocations with a 60-second scale-out cooldown — aggressive enough to be expensive in production if left untuned.

The security posture has two gaps: the NGC API key is passed as a plaintext environment variable on the SageMaker model resource (visible in the AWS console and API to anyone with `DescribeModel` permission), and the execution role gets `AmazonSageMakerFullAccess` which grants far more permissions than the endpoint needs at runtime.

The deploy script extracts the AWS region from the endpoint URL via a GNU-only Perl regex rather than reading it from a Terraform output. The load test moves from async HTTP to boto3, but the shared `stats` dictionary is mutated concurrently from thread pool workers without synchronization — counts will drift under high concurrency.

<details>
<summary>Issues (4)</summary>

1. **NGC API key in plaintext environment** — The key is set as a plain `environment` map value on `aws_sagemaker_model`. Use AWS Secrets Manager or SSM Parameter Store and grant the execution role access to retrieve it, or at minimum document this as a known limitation for demo purposes.
2. **Overly broad IAM policy** — `AmazonSageMakerFullAccess` grants permissions to create/delete any SageMaker resource. Scope to a custom policy allowing only `sagemaker:InvokeEndpoint`, ECR pull, CloudWatch logs, and S3 model artifact access.
3. **Thread-unsafe stats accumulation** — `stats["ok"]`, `stats["err"]`, and `stats["latencies"].append()` are called from worker threads without a lock. Under high concurrency, counts can be lost and the latencies list can raise or silently corrupt. Use a `threading.Lock` or collect results via `Future.result()`.
4. **Fragile region extraction in deploy.sh** — `grep -oP '(?<=sagemaker\.)[^.]+'` on the endpoint URL is a Perl regex that won't work on macOS grep. The region is already a Terraform variable — add a `region` output or read `var.region` directly.

## NGC API key exposure in SageMaker model environment

The `aws_sagemaker_model.nim` resource passes `NGC_API_KEY = var.ngc_api_key` as a container environment variable:

```hcl
primary_container {
  image = var.nim_container_image
  environment = {
    NGC_API_KEY     = var.ngc_api_key
    NIM_SERVER_PORT = "8080"
    NIM_MODEL_NAME  = "meta/llama-3.1-8b-instruct"
  }
}
```

Although `var.ngc_api_key` is marked `sensitive = true` in variables.tf (hiding it from plan output), the value is stored in plaintext in the SageMaker model definition. Anyone with `sagemaker:DescribeModel` permission on the account can read it from the API response. The fix is to store the key in AWS Secrets Manager, pass the secret ARN as an environment variable, and have the container retrieve it at startup — or use SageMaker's native integration with Secrets Manager if the NIM container supports it.

## IAM role grants full SageMaker control

The execution role attaches `AmazonSageMakerFullAccess` plus `AmazonEC2ContainerRegistryReadOnly` (the latter is redundant — already included in the former). The SageMaker endpoint execution role only needs ECR pull, CloudWatch Logs write, and optionally S3 read for model artifacts. Attaching `FullAccess` means a compromised container or misconfigured endpoint could create, modify, or delete any SageMaker resource in the account.

## Deploy script region extraction

```bash
REGION=$(terraform output -raw endpoint_url | grep -oP '(?<=sagemaker\.)[^.]+')
```

Two problems: `grep -P` (Perl regex) is GNU grep-specific and fails on macOS which ships BSD grep. The region is already a Terraform input variable — parsing it back out of a synthesized URL is unnecessarily fragile. Add `output "region" { value = var.region }` and use `terraform output -raw region`.

## Thread safety in load_test.py

```python
def send_request(client, endpoint_name, stats):
    ...
    stats["ok"] += 1
    stats["latencies"].append(latency)
```

`stats["ok"] += 1` is a read-modify-write sequence (LOAD, ADD, STORE) — not atomic under Python's GIL. With a `ThreadPoolExecutor` of up to 200 workers, the final counts will under-report successful requests. The fix is either a `threading.Lock` around the mutations, or — cleaner — have each worker return `(latency, success)` and aggregate results in the main thread after `as_completed`.
